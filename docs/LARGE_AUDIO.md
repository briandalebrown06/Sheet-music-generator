# Large files and long recordings — section 1

Implemented and checked locally on 2026-10-27. The defaults are **500,000,000 bytes (decimal 500 MB)** and **3,600 decoded seconds (60 minutes)**. These apply independently to the complete original, even when selecting a short excerpt. Inputs exceeding either ceiling fail explicitly; successful results do not represent only the first five minutes.

## End-to-end implementation

- **Browser:** native metadata/playback avoids decoding the full waveform into Web Audio. Inputs above 8 MiB use bounded, checksummed, resumable requests. Real byte progress, pause, retry and resume are separate from analysis stages. Reloading the same tab and reselecting the same file resumes verified chunks; changed files cannot reuse mismatched bytes. A browser-incompatible source uploads once and uses a protected, range-capable FFmpeg preview URL. Microphone audio follows the same size/duration limits after stopping; real-time 60-minute hardware microphone capture has not been measured.
- **API/storage:** per-account, idempotent upload sessions live in SQLite and private UUID directories. Only verified/fsynced chunks advance the durable offset. Finalization verifies all hashes and the full byte count, moves the preserved source without copying it, and publishes one project/job transaction. Completion/retry survives a crash after the move. File signatures, actual decoding and complete-source duration are validated independently. Existing multipart clients remain supported, with bounded private disk spooling. See [the transfer protocol](RESUMABLE_UPLOADS.md).
- **Proxy/deployment:** Caddy allows 500,065,536 bytes including multipart overhead, and the new client normally sends 8 MiB requests. Longer bounded decoder/proxy/worker timeouts, private volume-backed scratch, storage quotas and free-space preflight are configured together. Compose and Caddy configuration validation passed. Linux container execution and any additional hosting proxy still require staging validation.
- **Analysis:** Basic Pitch receives model-appropriate overlapping windows from disk. Exact sample-based frame timestamps replace nominal-frame-rate trimming that could omit the tail on long clips. Disk-backed global activations preserve timing; note extraction happens once across the complete timeline to avoid independent-window note duplication. Sustains/reattacks are still subject to model errors. pYIN contexts and UMX separation windows also checkpoint real output and retain absolute offsets. The canonical score continues to use one consistent tempo/meter configuration; expressive tempo maps are outside section 1.
- **Recovery/cleanup:** each completed model window has an atomic checkpoint keyed by audio/model/runtime/settings. Interrupted jobs resume within the existing attempt budget; stale workers cannot publish. Completion/cancellation reclaims checkpoints, failed checkpoints expire after 24 hours, and project deletion removes them. Unfinished uploads expire after 24 idle hours; the running worker reclaims abandoned data after leases release. See [retention details](RETENTION.md).
- **Waveforms:** bounded sample blocks are reduced to at most 2,000 bins over the whole selected duration, including the last sample.

No new model, dependency, or weight license was introduced. The installed Basic Pitch 0.4.0 ONNX runtime is still used. Relevant verified implementation references: [Spotify model windowing](https://github.com/spotify/basic-pitch/blob/v0.4.0/basic_pitch/inference.py), [FFmpeg processing controls](https://ffmpeg.org/ffmpeg.html), [XHR upload progress](https://developer.mozilla.org/en-US/docs/Web/API/XMLHttpRequest/upload), and [Caddy request-size configuration](https://caddyserver.com/docs/caddyfile/directives/request_body). Code and model licensing remains documented in [DEPENDENCIES.md](DEPENDENCIES.md) and [SEPARATION_ENGINE.md](SEPARATION_ENGINE.md).

## Actual 12-minute HTTP → model → MIDI test

Machine: macOS 27.0.1 arm64, Python 3.11.18, 10 logical CPUs. Original procedural development audio is generated by `scripts/generate_long_fixture.py` (CC0); expected notes are used only for evaluation after real inference. No reference notes enter model output.

| --- | --- |
| Original WAV | 720.000 seconds; 44,100 Hz stereo PCM16; **127,008,044 bytes** |
| SHA-256 before/after transfer | `1cc36e786f1c6c3e11c1c6f6824a75d2561da0e343a67f32b1154684fc63940a` — identical |
| Interrupted transfer | Partial request discarded; committed offset persisted across actual API restart; identical replay accepted |
| Finalization | Repeated request returned the same project, without a duplicate job |
| Worker restart | Supervisor force-killed during real inference; replacement completed attempt 2 and reused 24 model windows |
| Timeline coverage | 15,876,000 normalized input frames; all **720 seconds**; 440 model windows |
| Last activation timestamp | 719.9998185941043 seconds |
| Ending reference note | MIDI pitch 72, 718.4–719.8 seconds |
| Ending detected note | Pitch 72, 718.4061678004535–719.8341950113379 seconds |
| Ending raw-MIDI note | Ends at **719.8340909090908 seconds** after MIDI tick serialization |
| Waveform | 2,000 bins covering the complete duration, including ending audio |
| Completed worker wall time | 18.531 seconds, including the forced restart/recovery |
| Completed analysis process | Peak RSS 971,063,296 bytes; 42.797 CPU seconds (multiple CPU threads) |

Resource measurement is scoped to the completed analysis process, excluding the API, supervisor, decoder subprocesses and failed first attempt. Wall time includes restart. Concurrent development work and a synthetic waveform make this a single observation, not a latency promise or capacity benchmark for a Linux server.

The model produced **791 cleaned detections** for **537 reference notes**. All 537 pitches/onsets matched within 150 ms, with mean absolute onset error 0.003901 seconds; **254 extra detections remained**. This is evidence of full coverage, not perfect musical accuracy. It does not establish accuracy on commercial songs or acoustic recordings. Full machine-readable results, including activation intervals and separate boundary checks: [large-audio-audit.json](../evaluation/large-audio-audit.json).

## Independent boundary checks

| Boundary | Real bytes/decoder test |
| --- | --- |
| 500,000,000 bytes | A valid one-second WAV padded with a legal JUNK chunk was fully transferred over HTTP, checksummed and finalized; the actual application decoder then read its one-second audio |
| 500,000,001 bytes | Declared excess rejected; an actual extra byte beyond a complete accepted session was also rejected |
| 3,600 seconds | A real 14,400,044-byte, 4 kHz mono PCM8 WAV decoded as exactly 3,600 seconds and was accepted by duration validation |
| 3,600.1 seconds | The same encoding, 14,400,444 bytes, was rejected for duration despite being below the old file-size limit |

The byte-boundary WAV padding deliberately isolates size from duration. The duration-boundary files are silent decoder fixtures, not successful musical transcriptions; silence validation is covered separately. The main 12-minute performance exceeds **both** old limits with actual musical waveform data. These tests do not imply a one-hour commercial mix has been successfully separated or engraved.

## Additional real one-hour model check

A separate CPU run used the same generated performance looped five times, decoded by FFmpeg to mono 22,050 Hz PCM16: **158,760,078 bytes, 79,380,000 frames, exactly 3,600 seconds**. Actual Basic Pitch completed all **2,196 windows** and **311,691 activation frames**, with contiguous coverage from 0 to 3,600 seconds and a last activation at 3,599.999093 seconds. The final C5 was detected at 3,598.405442–3,599.833469 seconds; raw MIDI ended at **3,599.834091 seconds**. All 4,590 raw note events appeared in MIDI; cleanup retained 3,960 notes.

This took **95.650 seconds wall time**, **262.692 CPU seconds**, and **2,637,561,856 bytes peak RSS (2.46 GiB)** on the same Mac. The scope is the real adapter plus raw MIDI, excluding API, worker recovery, notation and the FFmpeg child. The 12-minute audit above covers the complete HTTP/worker path. This one-hour result does not claim one-hour sheet-music engraving or mixed-source separation.

Post-analysis comparison matched all 2,685 repeated synthetic references within 150 ms, with 1,275 extra cleaned detections, mean absolute onset error 0.003900 seconds and mean absolute end error 0.042527 seconds. See [hour-capacity-audit.json](../evaluation/hour-capacity-audit.json). This remains a synthetic capacity/coverage check, not evidence of commercial-song accuracy.

## Browser and regression verification

The large-upload Chrome audit passed **28 assertions** with a second real generated 720-second WAV (31,752,044 bytes; SHA-256 `7a07fc601ceada2af12157d0d680519ae86986cf2d0029ffd2b6061086fda09b`). It verified a lost response after a committed chunk, pause/reload/reselect, resume without retransmitting the prefix, hash buffers no larger than 8 MiB, a protected streamed preview, playback at 719.1 seconds, clip selection without a second transfer, and a persistent project. It uses isolated API/worker/frontend data, never the user's recordings.

The existing audio-input browser regression passed **90 assertions**, including real generated WAV/MP3/M4A/FLAC playback/upload, Chromium test-microphone capture/submission and track cleanup. Browser error simulations are labeled in that runner. These are Chrome automation tests; no physical microphone, Safari, Firefox, or real mobile-device capture was tested.

The authenticated browser regression passed **68 assertions**, including real inference, edit/save/reopen, MusicXML/MIDI/PDF, two-account authorization, deletion, keyboard operation and a mobile viewport. TypeScript, production build, Prettier, dependency consistency, Caddy validation, Compose validation and whitespace checks passed. The existing OSMD bundle-size advisory remains.

The full Python suite with real model/separation tests enabled passed **254 tests**, with two upstream deprecation warnings. It covers decoder errors/silence, ownership/CSRF/quotas, chunk integrity and crash recovery, cancellation, model checkpoints, waveform coverage, original/edited exports and existing review workflows. Review found and fixed a corrupt compressed-checkpoint retry loop: damaged DEFLATE data is now a cache miss and the window is recomputed. A new regression verifies recovery.

The live local API and worker were restarted while idle. Health reports `max_upload_bytes: 500000000`, `max_duration_seconds: 3600`, resumable-upload capability and an online worker. The browser upload screen was inspected and displays **500 MB · 60:00**; an existing completed project still renders its saved score and download actions.

## Reproduce

From the repository root with the existing Python/Node setup:

```sh
# Exact app defaults; restart both API and worker after changing .env.
# MAX_UPLOAD_BYTES=500000000
# MAX_DURATION_SECONDS=3600

# This script uses a temporary DATA_DIR and loopback port 8003 by default.
# It generates the 127 MB fixture, transfers it, interrupts/restarts its own
# processes, checks real Basic Pitch/MIDI, and separately tests both limits.
.venv/bin/python scripts/audit_hour_support.py

# Separate actual one-hour adapter/raw-MIDI capacity check; no live data touched.
.venv/bin/python scripts/audit_hour_capacity.py

# Generate the same playable source separately for manual UI testing.
.venv/bin/python scripts/generate_long_fixture.py /tmp/scorecraft-long-fixture

# Browser runners use disposable services on 8001/5174; run them sequentially.
AUDIO_TEST_PYTHON="$PWD/.venv/bin/python" FFMPEG_BINARY="$PWD/.runtime/bin/ffmpeg" pnpm -C scripts test:large-upload
AUDIO_TEST_PYTHON="$PWD/.venv/bin/python" FFMPEG_BINARY="$PWD/.runtime/bin/ffmpeg" pnpm -C scripts test:audio

DATA_DIR=/tmp/scorecraft-large-test-default-app PATH="$PWD/.runtime/bin:$PATH" \
  RUN_MODEL_TESTS=1 RUN_SEPARATION_TESTS=1 .venv/bin/python -m pytest \
  backend/tests scripts/test_evaluation.py scripts/test_mixed_evaluation.py -q
pnpm -C frontend typecheck
pnpm -C frontend build
pnpm -C frontend format:check
```

`audit_hour_support.py` uses the installed repository `.runtime/bin/ffmpeg`; set up that existing runtime first or adjust its executable setting for a different machine. `--fixture DIR`, `--output DIR`, `--port PORT`, and `--skip-boundaries` are available. The older `audit_long_recordings.py` deliberately pins a 300-second configuration to reproduce the historical audit; it does not describe current defaults.

## Remaining constraints and launch checks

- The full raw notes and performance MIDI are retained, but the current editor/notation accepts at most **10,000 notes**, and notation has a **10,000-measure** cap. A sparse one-hour 120 BPM score spanning 1,800 measures is covered by a canonical-model test. Dense long recordings may exceed editing/engraving limits; the application reports this and does not export a prefix as a complete score. PDF retains its 100-page limit.
- Global note extraction still uses memory proportional to duration; model-window decoding is streamed. A machine without sufficient RAM/disk fails explicitly rather than silently shortening the input.
- One-hour physical microphone recording, one-hour mixed separation, production proxy uploads, Linux container inference, GPU performance and concurrent-user load remain unmeasured. Test those on the intended target before advertising them as verified. No public deployment was performed.
- Caddy and Compose configuration validation passes; Docker Engine is unavailable here, so container build/startup and live-domain TLS remain deployment gates. See [DEPLOYMENT.md](DEPLOYMENT.md).
